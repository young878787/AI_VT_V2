# AI_VT 架構整合調整計劃

- 日期：2026-09-23
- 目標架構：[AI_VT_Architecture_Summary.md](./AI_VT_Architecture_Summary.md)
- 依據：本日工作樹的程式碼；目標文件中尚未提交的補充內容也納入規劃。

## 計劃摘要

- 問題理解：將現有「JEV Emotion → Chat／JEV Action → 同步 Memory Agent → Live2D」流程，逐步整合成目標文件的 Chat、JEV、Runtime State、Action Scheduler、背景 Memory 五個責任。已實作的元件直接沿用；輸入被接受時即送出背景記憶事件。
- 影響範圍：`/ws/chat` 編排、情緒與 session 狀態、Chat 串流、expression plan 的套用路徑、記憶寫入與讀取。語音輸入沿用現有聊天入口，Cubism SDK 原始碼不動。
- 建議方案：保留現有程式分層，先修資料流及相容問題，再補 Scheduler 與結構化記憶；每階段均可單獨驗收和回退。
- 實作步驟：基線／單一表情入口 → 輸入與 Runtime State → 真正的 Chat 串流及背景記憶 → Scheduler／Live2D adapter → 記憶分類、整理、檢索及情緒趨勢。
- 驗證方式：以現有 `unittest`、expression plan 契約檢查、TypeScript 檢查及隔離式 chat CLI 為基礎，補資料流順序、競態和失敗回退測試。
- 風險與假設：目前是單一使用者、本機單程序；`user_profile.json` 是全域資料。多使用者、分散式部署及其他 Avatar 引擎不在本輪落地範圍。文件中的 100–500 ms 即時動作是**收到計畫後的排程目標**，不能視為含遠端 JEV 呼叫的端到端保證。

## 2. 已定的架構決策

### 2.1 輸入、狀態與順序

1. **以現有六欄 Emotion State 為正式即時契約**：`shy`、`pleased`、`genuinely_angry`、`sad_or_hurt`、`masking_positive_feeling`、`wants_continue_interaction`。目標文件中的 `happy`／`shy`／`angry`／VAD 為概念示例，這次不擴充持久化 schema。JEV 的絕對分數先經 `resolve_emotion_state()` 驗證與回退；若分析需要 `emotion_delta`，由新舊快照相減產生衍生資料，不要求 JEV 改輸出。
2. **後端擁有對話與情緒的真值**：單連線即時狀態包含 `session_id`、`turn_id`、六欄 emotion、上輪 expression carry state、近期訊息及版本。`current_action` 的實際播放進度由前端 Scheduler 擁有，透過 `action_state` 回報開始／結束／取消，後端保存最後確認的快照供 JEV 參考；未回報時視為未知，不推測動作仍在播放。固定 Character State 沿用 `PERSONALITY`，Relationship State 先由 profile／記憶摘要提供文字線索，不虛構新的數值欄位。`appStore` 的情緒是顯示副本。啟用既有持久化設定時才跨重連還原；未啟用時狀態跟隨連線，不暗中寫檔。
3. **延續現有 JEV 先行順序**：Input 正規化時固定一份對話／profile／記憶的唯讀快照，先從現有 profile 與 notes 選出有長度上限、與本輪訊息相關的記憶，避免背景 Memory worker 更新快取後改變本輪 Prompt。JEV Emotion 接收使用者訊息、近期對話、上輪情緒及這份相關記憶；更新 Runtime State 後，Chat 與 JEV Action 並行，兩者共用同一份已驗證 emotion 與記憶快照。JEV Action 只決定結構化表演意圖，Chat 只決定對白。這解決目標圖上「Chat／JEV 並行」與「Chat 讀取新情緒」的先後矛盾。JEV 超時仍用上一輪／neutral 回退；之後不得用遲到結果覆蓋較新一輪。
4. **Input Processor 是純轉換邊界**：接受既有 `/ws/chat` 文字格式及 ASR 完稿轉入的文字，正規化 `text`、有效 `session_id`、伺服器時間、輸入來源和本輪 `turn_id`；`action_state`、sync、reset 經控制訊息路徑，不送入 Chat Prompt。目前沒有可靠的使用者身分系統，內部一律視為 `default_user`；不把前端傳來的任意 `user_id` 當隔離依據。
5. **同一 session 只有一個有效對話輪次，接收端持續運作**：前端送出訊息時先產生 `turn_id`，後端驗證後在所有文字／情緒／Action／TTS 事件回傳；舊客戶端未提供時由後端產生並回報。`/ws/chat` 的 reader 持續接收控制訊息和新輸入，單獨的 turn task 執行 JEV／Chat／Action；同一 session 新輸入採「最新一輪優先」，取消尚未完成的舊輪並回傳 `turn_cancelled`，已接受的使用者輸入事件仍交由 Memory Judge 判斷，除非 reset。前端在送出新訊息當下即取消舊動作，並對舊 `turn_id` 的**所有**回傳（含 `text_stream`、`emotion_update`、`stream_end`、Action、TTS）做過期過濾，不等待後端確認；`currentAssistantMessageId` 必須與 turn 綁定，避免兩輪文字合併。所有並行 task 的 WebSocket 寫入需有單一送出鎖。Reset 也取消輪次、清除待播動作與 emotion；手動控制和模型切換通知 Scheduler 取消或重新綁定。

### 2.2 Chat、動作與相容

6. **Chat 只產生可唸文字，預設不用 thinking，輸入有固定預算**：保留 `build_agent_a_prompt()`，不給 Chat 表情或記憶寫入工具；沿用現有 `NO_THINKING_EXTRA_BODY` 的 provider 對應設定，對支援的模型明確關閉 thinking，其餘 provider 選用無內部推理輸出需求的快速 Chat 模型。對話上下文先限最近 8 輪、已完成的 session 摘要、六欄情緒摘要及與 JEV 同源的有界關聯記憶，不再把目前最高可達 230,000 tokens 的完整訊息列表直接交給快速 Chat 模型。依實際選用模型設定 `CHAT_CONTEXT_TOKEN_BUDGET`，超額時先裁舊對話並使用上一份已完成的摘要，不等待本輪壓縮。把 `collect_agent_a()` 換為逐段送 `text_stream`，但必須在送出前處理 `<think>`／舊狀態標籤，避免半段標籤或內部推理洩到 UI／TTS；若模型無法安全逐段清理，就對該模型使用收集後送出的保守路徑。`stream_end` 僅表示文字完成，不等待記憶整理或語音播放。
7. **一輪表情以 `expression_plan` 為唯一正常輸出**：它已覆蓋 Immediate（`basePose`／`microEvents`）、Sequence（`sequence`／`motionPlan`）和 Recovery（`idlePlan`／回到 base）。舊 `behavior` 與獨立 `blink_control` 短期只供明確舊客戶端使用；現有主頁及 OBS 鏡像不得重複套用。`speakingRate` 直接取 plan，無須為 TTS 生成一次舊 payload。
8. **Scheduler 設在前端、模型寫入之前**：`wsService → Action Scheduler → Live2D adapter → LAppModel`。Scheduler 管理整個 plan 的優先權、中斷、排隊和冷卻；`LAppModel.update()` 繼續負責每幀插值、物理及最終參數寫入。`MotionController` 既有 Cubism 優先級留給 motion 播放，不能替代跨表情／idle／手動控制的 Scheduler。
9. **初始排程政策**：手動操作優先級 100、緊急反應 80、一般對話 50、idle 10；同一輪的 Immediate 與 Sequence 為一個 action，Recovery 隨 action 結束接續。較高優先級可以中斷可中斷 action；不可中斷的短動作完成後再取最新的待執行計畫；同類短反應在冷卻期合併為最後一個，不無限排隊。缺省 plan 為一般對話、可中斷；關鍵欄位由 Planner 的規則表決定，JEV 不直接輸出任意數值。Scheduler 回報帶 `turn_id`／`action_id` 的 `started`、`finished`、`cancelled`，讓後端的 `current_action` 有來源可查。
10. **模型替換只改真正的模型邊界**：可選的 `CHAT_AI_PROVIDER`／`CHAT_MODEL_NAME`、`MEMORY_AI_PROVIDER`／`MEMORY_MODEL_NAME` 分別覆蓋原設定；未設定時兩者沿用 `AI_PROVIDER`／目前 provider 對應的 `MODEL_NAME`。背景 Memory 可選較慢的雲端模型，JEV 延用現有 System One；新設定不得使舊 `.env` 無法啟動。`Hiyori.json` 仍是 Live2D schema 來源；不手改產生的 `src/generated/tools.ts`。其他 Avatar 要先有實際需求，再把目前 compiler 中的 Live2D 映射抽成第二個 adapter。

### 2.3 記憶與資料治理

11. **背景工作從使用者輸入分支，不阻塞文字**：Input Processor 接受訊息後即持久化最小的 Interaction Event（使用者文字、session／turn id、時間、最近對話快照），排給 Memory worker；Chat 成功時可附上回覆供整理參考，但 Judge 的保存判斷以使用者輸入為主，不等待回覆。Chat 失敗或被打斷時，該使用者輸入仍可被判斷；`stream_end` 只與 Chat 完成有關。若待辦檔寫入失敗或容量已滿，記錄明確錯誤並讓 Chat 繼續，不能悄悄丟失事件或讓對白無限等待。Memory worker 沿用現有 `build_memory_prompt()`（讓回覆可為空）、`call_memory_agent()`、工具參數清理及 `execute_profile_update()`／`append_memory_note()`。先沿用既有 Memory Agent 作 Judge，避免再加第三次 JEV 呼叫。記憶模型失敗只記錄任務錯誤，不撤銷已完成的聊天。
12. **背景任務要可追蹤、可重跑及逐項去重**：MVP 以本機原子寫入的待辦檔保存 event id、reset epoch、Judge 決策、每個工具操作的 deterministic operation id／狀態；worker 有界併發（初始 1）及重試上限，啟動時補跑未完成項。不能只在待辦檔寫「完成」來宣稱無重複：profile 更新須把已套用 operation id 與資料一起原子寫入，memory note 須把 operation id 與內容一起原子寫入，重跑時檢查資料檔中的 id。單程序鎖須序列化 reset 與寫入，reset 先增加 epoch；舊 epoch 任務即使稍後完成 LLM 呼叫，也不得再提交。寫入成功後才發內部 `user.update`（profile）或 `memory.update`（記憶）事件，欄位含 `event_id`、`turn_id`、`changed_fields`／`memory_ids`、`revision`。先供後端快取失效與診斷使用；只有 UI 真正需要時才映射成新的 WebSocket 訊息。此方案限本機單程序；若轉成多 worker／多主機，應先換可交易的持久儲存。
13. **短期摘要不當成長期事實**：原本 `compress_context()` 寫入 `memory.md` 的「對話摘要」改存 session 專用摘要，重連後可還原；長期記憶只由 Judge 判定後進入。保留舊 `memory.md` 的讀取相容，遷移前先備份，避免既有回憶消失。
14. **記憶類型與保留規則**：短期＝session 訊息與摘要；長期＝偏好／人物／持續事實；特別＝生日、承諾、重大事件。Judge 回傳 `store`、`type`、0–1 `importance`、`ttl`（`session`／`long`／`forever`）；後端驗證並決定是否採納。先維持 `user_profile.json` 與 `memory.md`，當分類／importance／TTL 需要正式儲存時，新增單一原子寫入的 `memory_records.json`；舊 `memory.md` 一次性匯入並去重，此後作相容檢視而非第二份真值。每筆含 `id`、`type`、`text`、`importance`、`created_at`、`last_accessed_at`、`access_count`、`expires_at`、`protected`、`source_turn_id`、`status`。`session` 不進長期檔；特別記憶預設 `protected=true`、不過期；普通記憶不自動永久刪除。
15. **檢索與遺忘分開計分**：Chat 先以中文雙字片段／英文單詞命中數及近因排序，最多取 5 筆、合計最多 800 字的相關記憶，再視實際品質考慮向量檢索。保留分數初版固定為 `0.7 × importance + 0.2 × 2^(-age_days/30) + 0.1 × min(access_count/5, 1)`；非 protected 紀錄須存活至少 30 天且分數低於 0.25 才轉為 archive，`expires_at` 到期也先 archive，不自動刪除。這組初始值由隔離 CLI 的記憶案例檢視後再調整。摘要／合併工作只處理已判定要存的紀錄，並記錄來源 ID、禁止悄悄覆蓋 protected 記憶。長期 Emotion Pattern 以可回溯的多輪趨勢產生，不把單輪六欄分數直接寫進長期記憶。

## 3. 目標資料流與責任邊界

```text
AIChatPanel 或 voiceWsService → wsService → /ws/chat
                                           ↓
                                    Input Processor
                               ┌───────────┴───────────┐
                               ↓                       ↓
                   Interaction Event 持久待辦   Context Snapshot
                                             （近期對話＋相關記憶＋前一輪狀態）
                               ↓                       ↓
                       背景 Memory Judge        JEV Emotion（限時）
                               ↓                       ↓
                   user.update／memory.update   Runtime State 更新／版本化
                             （內部）               ┌──────┴──────┐
                                                   ↓             ↓
                                        Chat Engine 串流      JEV Action
                                        text_stream ↓             ↓
                                          stream_end       expression compiler
                                                               ↓
                                                        expression_plan
                                                               ↓
                                                     前端 Action Scheduler
                                                               ↓
                                                         Live2D adapter
                                                               ↓
                                                            LAppModel
```

`stream_end` 可早於 `expression_plan` 到達；兩者以 `turn_id` 對齊。TTS 可在文字完成後開始，不等待背景 Memory；若尚無 Action 的 `speakingRate`，使用 1.0，晚到的動作不重播已送出的語音。新輸入可打斷未完成的舊輪；被打斷的輪次發 `turn_cancelled` 而不發 `stream_end`，已接受的輸入仍可進入背景記憶。前端／後端 reset、斷線及模型切換都必須取消或忽略過期結果。

## 4. 分階段施工與驗收

### P0 — 建立基線、消除重複動作（先做）

1. 鎖定目前 WebSocket 訊息順序、`expression_plan` 格式、JEV fallback、Chat 回覆與記憶檔行為；用既有隔離 CLI 記下首字、文字完成、Action 到達及記憶完成時間。→ 驗證：`test_emotion_chat_ws`、`test_expression_compiler`、`check-expression-plan.mjs` 通過，報告能重現現況。
2. 主頁僅按 `expression_plan` 套用一次，blink 也僅按 plan 執行一次；確認 `/display` 採 Canvas 鏡像而非第二套 Live2D 播放。舊 payload 先保留協議相容，但新客戶端忽略同輪重複項；確認無舊消費者後停止發送。→ 驗證：同一輪 `applyBasePose`、blink 只呼叫一次；Debug Panel、手動控制與 OBS 畫面正常。
3. Chat 呼叫改用不啟用 thinking 的 provider 設定，設定短回覆的輸出上限；JEV Emotion／Action 與現有 Memory Agent 呼叫保持分離。→ 驗證：Chat 請求不再帶啟用 thinking 的 `EXTRA_BODY`，純文字回覆、JEV 表情與記憶功能仍通過現有測試。

### P1 — Input Processor 與 Runtime State

1. 在後端路由與 domain 之間加入純函式的輸入正規化；沿用 `normalize_session_id()`，拒絕空訊息、保留現有 chat／sync／reset。前端產生 `turn_id`，後端驗證／回報；ASR 完稿仍進 `wsService.sendMessage()`。從既有 profile／notes 建立有界相關記憶快照，補進 JEV Emotion／Action context，Chat 使用同一來源；JEV 不讀完整記憶檔。→ 驗證：文字／語音等價、JEV 確實收到相關記憶但不超過預算、無效 session、重連及 reset 測試。
2. 把路由中的 emotion／expression／messages 管理收斂成每 session 的 runtime 服務；保留原子寫入的 `emotion_states/`。新一輪複製固定的對話／profile／記憶快照，JEV 成功或 fallback 後原子更新 emotion 版本，再將同一版交給 Chat 與 Action。將 reader 與 turn task 分開，控制訊息可在 API 呼叫期間處理；新輸入採最新一輪優先並取消舊輪。→ 驗證：背景記憶寫入不改變已啟動的 Chat Prompt、並行工作讀到相同版本、兩個 session 隔離、連續輸入時只有新輪可送 Action、reset 即時生效、舊輪結果不覆蓋新輪。

### P2 — 真正串流與背景記憶

1. 把 session 摘要從長期 note 拆出，建立有 token 預算的 ChatContext（最近 8 輪＋已完成摘要＋有限記憶）；接著把 Chat 的收集式串流改成安全逐段轉送，對 `<think>` 與舊標籤使用跨 chunk 緩衝；完整回覆仍追加到對話歷史。`stream_end` 緊接文字完成，與 Action、Memory、TTS 解耦。→ 驗證：Chat 維持不請求 thinking、超長歷史仍不超過模型 context window、模型逐字／切碎標籤時不洩漏內容、延遲 Memory mock 不推遲 `stream_end`、Chat 失敗時不保存半輪回覆。
2. 以持久待辦和單 worker 移動現有 Memory Agent；事件在輸入被接受時就建立，回覆為可選脈絡；Judge 決策先落盤，再逐項執行具 operation id 的寫入。維持 `AI_VT_MEMORY_DIR` 的隔離能力，讓 CLI 可等到對應 `event_id` 完成再量測記憶變更。→ 驗證：Chat 失敗／被打斷時仍可判斷使用者事實；在「LLM 決策已落盤」、「資料已寫但待辦未標完成」等位置模擬中斷及重啟，重跑不重複寫入；CLI 測試記憶不碰正式目錄；reset 後舊 epoch 任務不得回填已清空的資料。
3. Chat／Memory 角色模型設定分開，預設回退到目前 provider／model。先不指定新的實際模型名稱或購買新服務；以 P0 的延遲與回覆品質基線挑選快速模型。→ 驗證：舊 `.env`、各 provider fallback 和新設定的單元測試。

### P3 — Action Scheduler 與 VT Adapter

1. 在前端增加 Scheduler，讓 WebSocket、Debug Panel、手動操作和自動 idle 都經單一仲裁入口；依既定優先級執行／中斷／冷卻，限制待辦最多只留最新一般對話 action。Live2D adapter 包裝目前 `appStore.setExpressionPlan()` 的模型呼叫；`action_state` 回報同步後端快照。→ 驗證：連續訊息、手動動作打斷、不能中斷的短動作、reset、切模型及過期 `turn_id` 測試。
2. 沿用 compiler 的 `sequence`、`motionPlan`、`idlePlan`；只補明確缺的 cancel／recovery 操作，對 `LAppModel.update()` 做局部修改。→ 驗證：100–500 ms 的**前端接收後**立即反應目標、結束後回 idle、眨眼／口型／物理與自動播放無衝突。

### P4 — 結構化記憶與關聯讀取

1. 在現有工具參數驗證後加 Judge 分類與 importance／TTL／protected 的規則檢查；不能由模型直接決定覆寫或刪除。匯入舊 `memory.md` 時保留備份、來源與去重記錄。→ 驗證：舊資料可讀、匯入可重跑、特殊記憶不衰減、profile 與 notes 不交叉汙染。
2. 由背景工作整理重複紀錄、生成 session 外的長期摘要；Chat 只取與當輪有關且有長度上限的記憶。遺忘先執行 archive 與可回復的檢視，不啟用自動刪除。→ 驗證：Prompt 長度有上限，關聯記憶命中且不混入其他 session 的短期摘要；整理失敗時原資料仍在。

### P5 — 長期情緒模式與進階動作（後續）

1. 用有來源輪次的彙總工作產生長期 Emotion Pattern，且僅在多次一致訊號時寫入；Chat 檢索時當作參考而非覆蓋即時 Emotion State。→ 驗證：單輪突發情緒不成為長期事實，reset 與使用者資料清除可刪除對應模式。
2. 擴充多段 Action Sequence 與更細的資源混合，只在現有 `expression_plan` 無法表達時才調整協議；若要加入第二種 Avatar，再抽離模型專屬 compiler／adapter。→ 驗證：長動作中斷、恢復、資源衝突與模型切換情境。

## 5. 階段完成條件、回退與文件同步

- 每階段須通過相關後端單元／整合測試；前端執行 `node scripts/check-expression-plan.mjs`、`node scripts/check-emotion-state.mjs`、`npm run build`（若本機 `spawn EPERM`，至少做 `npm run generate` 後的 `tsc -b`）。涉及 Chat／Memory 時跑隔離式 `tools/chat_test_cli.py`，檢查回覆、情緒、表情和最終記憶。
- 基線至少記錄 `input→emotion_update`、`input→首個 text_stream`、`input→stream_end`、`input→expression_plan`、`stream_end→memory job 完成`，比較 P0 與各階段。高延遲應能歸到 JEV、Chat、Action 或 Memory，不以未量測的「快速」作驗收說法。
- 每階段保留可回退邊界：P0 的舊協議可短期開啟、P2 的背景 worker 可停用並保留待辦、P4 的記憶匯入不刪舊檔。確認觀察期沒有舊客戶端後再刪相容碼。
- 實作完成後更新 [`README.md`](../README.md)、[`README.zh-TW.md`](../README.zh-TW.md) 與文件索引，移除「單一 LLM/tool call 同時控制表情與記憶」等過時流程描述；目標摘要維持概念架構，本文件維護實際落地順序。
