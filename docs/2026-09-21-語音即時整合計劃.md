# 語音即時整合計劃 — AI_VT_V2 × voice_txt

日期：2026-09-21
狀態：計劃（未實作）
來源專案：`voice_txt/`（即時語音助理試作，mic → VAD → ASR → LLM → Piper TTS 全鏈路已跑通）

---

## 1. 目標與範圍

把 `voice_txt/` 的兩項已驗證能力合併進 AI_VT_V2：

1. **即時語音輸入**：麥克風 → VAD 切段 → 本地 sherpa-onnx 串流 ASR → 文字進入現有聊天管線
2. **即時語音串流輸出**：LLM 回覆逐句切分 → Piper 本地串流合成 → 前端邊收邊播（口型同步沿用現有管線）

**不做的事（明確排除）**

- 不移植 `voice_txt` 的 LLM client（`llm.py`）、persona（`persona.py`）、對話歷史（`convo.py`）、終端 UI（`modes.py`/`repl.py`）— 這些由 AI_VT_V2 既有 chat_service / 記憶 / JPAF 管線承擔
- 不移植 `mic.py`（sounddevice 抓麥）— 改由瀏覽器抓麥經 WebSocket 送後端（理由見 D2）
- 第一版不做全雙工打斷（barge-in），列為 Phase 5 可選項

## 2. 現況分析

### 2.1 AI_VT_V2 現況（目標專案）

| 面向 | 現況 |
|---|---|
| ASR | **完全沒有**。`/ws/chat` 只收 JSON 文字；前端 `MicrophoneManager.ts` 已抓麥（48kHz、echoCancellation/noiseSuppression）但只算 RMS 音量做「自己的聲音動口型」，音訊從不離開瀏覽器 |
| TTS | `backend/tts_service.py` — Google Cloud Chirp 3 HD，**整檔 MP3** base64 經 `/ws/chat` JSON 下發（`{"type":"voice",...}`），在 `stream_end` 之後 fire-and-forget 送出。`synthesize_streaming()` 已寫但**從未被呼叫**。目前 `.env` `TTS_ENABLED=false` |
| 文字串流 | 目前用 buffered `collect_agent_a()`，全文一次以單則 `text_stream` 送出。**token 級串流器 `stream_agent_a()` 已存在但未啟用**（內建隱藏標籤過濾：`<thinking>/<think>/<thought>/<jpaf_state>/<emotion_state>`） |
| 前端播放 | `TTSPlayer.ts` 單發播放（每次新 `voice` 訊息先 `stop()` 再播）— **無佇列，不能接串流 chunk** |
| 口型 | `TTSPlayer` AnalyserNode RMS → `LAppModel.setLipSyncValue()` → `ParamMouthOpenY`。這條路徑與播放來源無關，串流 chunk 播放時**口型可直接沿用**。MotionSync 原始碼已 vendored 但未啟用 |
| 訊息順序 | 每回合：`jpaf_update` → `expression_plan` → blink → `behavior` → `jpaf_update` → `text_stream` → `stream_end` → `voice` |

### 2.2 voice_txt 現況（來源專案）

| 模組 | 內容 | 移植性 |
|---|---|---|
| `src/voice_txt/asr.py` | sherpa-onnx streaming transducer（`Luigi/x-asr-zh-tw-en-streaming-ft75m`，encoder.int8/decoder/joiner.int8/tokens.txt），`build_online_recognizer()` + `transcribe_online_streaming()`（切段後 0.5s chunk 餵入） | ★ 直接搬 |
| `src/voice_txt/vad.py` | Silero VAD v6 + `AutoGain`（AGC，目標 RMS 0.04）+ `SpeechSegmenter` 狀態機（`feed()` 進、端點出；silence 1.2s / min_speech 0.2s / max_turn 20s / pre_roll 0.5s）。**單執行緒餵入、與麥克風來源無關** | ★ 直接搬 |
| `src/voice_txt/tts.py` | Piper（`piper1-gpl`）`zh_TW-multi-voice.onnx`（speaker_id=1）+ `SentenceSplitter`（強切 `。！？!?\n\r`、弱切 `，、：；—…,;:` 需 ≥6 字、40 字硬切）+ `TTSWorker`（每回合建立 daemon thread 播放） | ★ 拆搬：Splitter + Piper 合成搬、sounddevice 播放**不搬**（改送前端） |
| `src/voice_txt/mic.py` | sounddevice 16k float32 抓麥 | ✗ 不搬（前端取代） |
| `src/voice_txt/llm.py` | OpenRouter 同步 httpx SSE | ✗ 不搬 |
| 其餘 | persona / convo / punct（CT-Transformer 標點，~5ms/句，可選）/ modes / repl | ✗ 不搬（punct 列可選） |

**架構差異（整合的核心難點）**

- voice_txt 是**全同步**架構：主執行緒吃麥克風、VAD、ASR、LLM，每回合開一條 TTS daemon thread，半雙工（播完才繼續聽）。AI_VT_V2 後端是 **asyncio**（FastAPI）
- voice_txt 的「串流 ASR」其實是**段落式**：VAD 判定說完才整段辨識，無即時部分結果（`OnlineRecognizer` 支援 incremental，只是沒做）
- 模型路徑解析基於套件位置（`Path(__file__).parents[2]`），搬移時需改為設定傳入

## 3. 關鍵架構決策

| # | 決策 | 建議 | 理由 | 拒絕的替代方案 |
|---|---|---|---|---|
| D1 | ASR 執行位置 | **後端 Python（sherpa-onnx）** | 直接複用 voice_txt 已驗證程式碼與模型，zh-TW 精度已實測 | 瀏覽器 Web Speech API（依賴 Chrome 雲端服務、離線不可控）；sherpa-onnx WASM（模型下載大、前端整合成本高） |
| D2 | 麥克風音訊傳輸 | **瀏覽器 getUserMedia → AudioWorklet 降採樣 16kHz Int16 → 新 WS `/ws/voice` binary 幀** | 瀏覽器自帶 echoCancellation/noiseSuppression；`MicrophoneManager.ts` 已有抓麥基礎；不綁定伺服器主機 | 後端 sounddevice 直接抓麥（無瀏覽器降噪、與現有「自己聲音動口型」功能衝突、跨機不可用） |
| D3 | TTS 引擎 | **Piper 本地合成為主（串流），Google Chirp3 為備援** | 本地零網路延遲、免 ADC 認證、免費、可無痛換 `voice_clone_onnx` 自訓聲音；Google `synthesize_streaming()` 存在但從未驗證且綁雲端 | 只用 Google streaming（延遲/成本/可用性不可控） |
| D4 | 串流粒度 | **逐句**（SentenceSplitter 邏輯原樣移植） | voice_txt 已驗證此粒度的聽感與延遲平衡 | 逐 token 合成（音調碎裂、合成次數暴增）；整段合成（首音延遲 = 全文生成完） |
| D5 | LLM 串流整合深度 | **分兩階段**：Phase 3 用 buffered 全文逐句串流；Phase 4 才切 `stream_agent_a()` token 串流 | Phase 3 動的檔案少、先驗證「合成→傳輸→佇列播放→口型」整條鏈；Phase 4 才碰 chat_ws 主流程與表情順序 | 一次到位 token 串流（LLM 串流 + 表情形管線 + 播放佇列三處同時改，除錯面太大） |
| D6 | 雙工模式 | **半雙工**：AI 說話期間前端閘門停送音訊；barge-in 列 Phase 5 可選 | 半雙工是 voice_txt 驗證過的體驗；避免喇叭聲被麥克風回收誤觸發 VAD | 直接做全雙工（需 AEC 調校與 ASR 抗噪驗證，風險高） |
| D7 | ASR 結果如何進聊天 | **前端收到 `asr_final` 後走既有 `sendMessage()` 打 `/ws/chat`** | `/ws/chat` 零改動；語音輸入與打字輸入在聊天層等價；兩條 WS 職責單純 | 後端內部直接轉發 chat 管線（把 ASR 連線與 chat 連線耦合在一起，訊息流混雜） |
| D8 | TTS 輸出格式 | **每句封裝成記憶體內 WAV（16-bit PCM）→ base64 → `voice_chunk` JSON** | 瀏覽器 `decodeAudioData` 原生支援、自帶取樣率資訊、實作最簡；本地場景頻寬不是問題 | 原始 PCM 裸流（前端要另帶取樣率 metadata、手動餵 AudioBuffer，易錯） |

## 4. 目標架構

### 4.1 語音輸入資料流（Phase 2 起）

```
[瀏覽器]
  MicrophoneManager（getUserMedia 48kHz, echoCancellation/noiseSuppression）
    → pcm-downsampler-worklet（AudioWorklet，48k→16k：3:1 平均，Int16）
    → voiceWsService（新）→ /ws/voice binary 幀（100ms = 1600 samples = 3200 bytes）
        ※ AI 播音期間：mic_state gate 停送（半雙工）
[後端]
  /ws/voice（backend/api/routes/voice_ws.py，新增）
    → 每連線一條 worker thread（queue.Queue 橋接 asyncio）
    → Int16→float32(/32768) → AutoGain → SpeechSegmenter.feed()
    → 端點 → np.ndarray 段落 → asr_engine（sherpa-onnx online，port 自 voice_txt）
    → asyncio.run_coroutine_threadsafe 送回：
        {"type":"asr_state",...} / {"type":"asr_final","text":...}
[前端]
  voiceWsService 收 asr_final → 顯示為使用者訊息 → wsService.sendMessage(text) 打既有 /ws/chat
```

### 4.2 語音輸出資料流（Phase 3 起，Phase 4 強化）

```
[後端 /ws/chat]
  Phase 3：collect_agent_a() 全文 → SentenceSplitter 切句
  Phase 4：stream_agent_a() token 逐 delta → SentenceSplitter.feed()
    → 成句丟入 asyncio.Queue
    → TTS 合成 worker（asyncio.to_thread 執行 Piper，記憶體內出 WAV）
    → {"type":"voice_chunk","seq":n,"audio":<b64wav>,"sentence":"...","final":bool}
    ※ expression_plan / behavior 順序不變（仍在 stream_end 前後發出）
[前端]
  TTSPlayer.ts 改造：chunk 佇列
    → 逐句 decodeAudioData → AudioBufferSourceNode 依 nextStartTime 排程接續播放
    → AnalyserNode RMS → setLipSyncValue()（口型路徑完全不變）
```

## 7. 分階段實作計劃

### Phase 1 — 後端引擎移植（不碰 WS，純庫 + 測試）

1. 移植 `asr_engine.py` / `vad_engine.py` / `piper_tts.py`，模型路徑全部由參數傳入
2. `config.py` 加 §6 設定；`requirements.txt` 加依賴；模型複製 + gitignore
3. 移植測試：VAD 切段/能量降級/AGC/SentenceSplitter 邏輯（voice_txt 測試已涵蓋「分塊餵入 ≡ 整批」parity，直接沿用）
   → **驗證**：`python -m unittest backend.tests.test_vad_engine backend.tests.test_sentence_splitter`；小腳本離線跑一段 wav 過 VAD+ASR、一句話過 Piper 出 WAV

### Phase 2 — 即時語音輸入（mic → 文字 → 聊天）

1. `voice_ws.py`（`/ws/voice`）+ `main.py` 註冊：worker thread 橋接、Int16→float32、AGC→VAD→ASR、`asr_state`/`asr_final` 回送
2. 前端：worklet、`voiceWsService.ts`、`MicrophoneManager` 擴充、`ControlPanel` 開關、`asr_final` → `sendMessage()`
3. 半雙工閘門：`isSpeaking` 時停送幀（`mic_state` control message）
   → **驗證**：手動 E2E（說話 → 文字出現 → 走完聊天回覆）；`npx tsc -b`；`npm run lint`；`node scripts/check-expression-plan.mjs`

### Phase 3 — 串流 TTS 輸出（buffered 全文 → 逐句播出）

1. `voice_stream_service.py`：全文切句 → 佇列 → `asyncio.to_thread` Piper 合成 → `voice_chunk` 依序發送（`final:true` 收尾）；`TTS_PROVIDER=google` 時走既有整檔路徑
2. `TTSPlayer.ts` 改 chunk 佇列 + `nextStartTime` 排程接續播放；`wsService` dispatch
3. 口型驗證：AnalyserNode 對每個 chunk 生效，`setLipSyncValue` 路徑零改動
   → **驗證**：聽感（句間無斷裂/爆音）、口型動作、`TTS_ENABLED/PROVIDER` 兩種設定都測

### Phase 4 — token 級串流（首音延遲最佳化）

1. `chat_ws.py` 改用 `stream_agent_a()`（隱藏標籤過濾已內建），逐 delta：發 `text_stream` + 餵 `SentenceSplitter`
2. `text_stream` 由單則改逐段 — 前端 append 語意需小改確認
3. **嚴格保持**：`expression_plan`/`behavior` 仍在 `stream_end` 前後的既有順序（表情形管線不動）
   → **驗證**：首音延遲 ≈ TTFT + 首句合成（voice_txt 實測約 3.3s 內）；表情 plan 契約測試全綠

### Phase 5 — 打磨（可選/漸進）

1. barge-in：`{"type":"tts_control","action":"stop"}` → 後端清句子佇列、前端 `stopAll()`
2. `ASR_USE_PUNCT` 標點後處理（port `punct.py`）
3. `asr_partial` 即時部分結果（`OnlineRecognizer` incremental API）
4. 錯誤降級：模型載入失敗 → 前端提示、聊天純文字模式不受影響
5. README / 文件更新
   → **驗證**：`python -m unittest discover`、手動全鏈路

## 8. WebSocket 訊息協議（新增部分）

### `/ws/voice`（新增連線）

| 方向 | 格式 | 內容 |
|---|---|---|
| C→S | binary | raw Int16LE PCM 16kHz mono，~100ms/幀 |
| C→S | JSON | `{"type":"mic_state","active":true\|false}`（半雙工閘門） |
| S→C | JSON | `{"type":"asr_state","state":"listening"\|"processing"\|"idle"}` |
| S→C | JSON | `{"type":"asr_final","text":"...","durationMs":1234}` |
| S→C | JSON | `{"type":"asr_partial","text":"..."}`（Phase 5 可選） |
| S→C | JSON | `{"type":"error","message":"..."}` |

### `/ws/chat`（既有連線擴充）

| 方向 | 格式 | 內容 |
|---|---|---|
| S→C | JSON | `{"type":"voice_chunk","seq":0,"audio":"<b64 WAV>","format":"wav","sentence":"你好呀。","final":false}`（最後一筆 `final:true`） |
| S→C | JSON | 既有 `{"type":"voice",...}` 保留（`TTS_PROVIDER=google` 時使用） |
| C→S | JSON | `{"type":"tts_control","action":"stop"}`（Phase 5 barge-in） |

## 9. 風險與注意事項

| # | 風險 | 對策 |
|---|---|---|
| 1 | `piper1-gpl` 未釘版本（voice_txt 已知缺口）；g2pW 缺檔會啟動時自動下載 | requirements 明確釘版；g2pW 預先複製進 `backend/models/` |
| 2 | VAD/ASR 是同步 CPU 工作，直接寫在 asyncio 事件迴圈會卡住整個後端 | 每連線獨立 worker thread + `queue.Queue` 橋接；SpeechSegmenter 非執行緒安全，**單執行緒餵入**是硬約束 |
| 3 | 迴聲：喇叭播出的 AI 聲音被麥克風收回誤觸發 VAD | 半雙工閘門（播音不送音）為第一道防線；瀏覽器 echoCancellation 為輔 |
| 4 | 延遲：Phase 3 首音 = 全文生成完 + 首句合成，體感偏慢 | Phase 4 切 token 串流後降至 TTFT + 首句合成（~2-3s）；兩階段分開驗收 |
| 5 | `chat_ws.py` 是表情形管線核心，改串流易破壞訊息順序契約 | Phase 4 嚴格保持既有訊息順序；上線前跑 `check-expression-plan.mjs` + `tsc -b` + 後端全測 |
| 6 | 兩套 TTS（Piper/Google）行為分叉：取樣率、語速參數、格式不同 | 統一 `voice_chunk` 為 WAV（自帶取樣率）；`PIPER_LENGTH_SCALE` 對應 `speaking_rate`；兩 provider 都要手動測過 |
| 7 | Piper 合成無上限佇列可能積壓（LLM 生成快於播放） | `voice_stream_service` 加 backpressure：佇列上限（如 8 句），滿時暫停餵句 |
| 8 | 現行 `.env` `TTS_ENABLED=false`，Google 路徑從未在現行設定下驗證 | Phase 3 驗證時兩種 provider 都實測；config import 時驗證設定合法性 |
| 9 | 本機已知 quirk：`npm run build` 可能 `spawn EPERM`（AGENTS.md）；後端建議用明確 Python 路徑 | 驗證以 `tsc -b` + lint + unittest 為主，build 失敗先判斷是否為環境問題 |
| 10 | sherpa-onnx / piper 的平台 wheel（Windows 主要開發環境） | Phase 1 先在實際開發機裝依賴跑通單元測試再往下走 |

## 10. 驗證計劃彙總

- **單元**：`python -m unittest discover`（VAD 切段 parity、AGC、SentenceSplitter、ASR 引擎 smoke）
- **前端契約**：`node scripts/check-expression-plan.mjs`、`npx tsc -b`、`npm run lint`
- **手動 E2E**：開語音模式 → 說話 → `asr_final` 文字正確 → 回覆逐句播出 → 口型同步 → 播放期間靜音麥克風
- **延遲量測**：對齊 voice_txt 慣例記錄 `ttft_ms` / `first_audio_ms`（每回合 log），Phase 3 vs Phase 4 對比
